# Проверка перед использованием

## Сборки

Проверяйте оба workflow, а не только наличие файлов в репозитории. Windows выполняет форматирование, тесты, Clippy и release build; macOS собирает iphoneos без подписи и проверяет ZIP IPA. IPA должен содержать `Payload/LocalDrop.app/Info.plist` и Mach-O исполняемый файл для устройства. Подпись и установка проверяются пользователем отдельно.

## Обязательные тесты на настоящих устройствах

- В одной LAN без доступа к интернету: QR → разрешение Windows → передача в обе стороны. Ручная вставка кода. Отказ/тайм-аут сопряжения. Новый QR после перезапуска. Неверный отпечаток/токен не должны работать.
- Пустой файл, файл больше 4 ГБ, 20 разных файлов, кириллица/эмодзи, одинаковые имена. Сравнить `Get-FileHash -Algorithm SHA256` исходника и результата, для iPhone экспортировать оригинал через Files для внешнего сравнения. Содержимое текстов, переносы строк и Unicode должны совпадать.
- HEIC, JPEG, RAW, HEVC, обычное видео и Live Photo. Проверить размеры/хеши оригинальных ресурсов; не сравнивать Live Photo с собранным контейнером. Отредактированное фото должно дать исходник.
- Оригинал только в iCloud: без разрешения сети — понятная ошибка, с разрешением и интернетом — оригинал. Отказ/ограниченное разрешение Photos, камера и локальная сеть. Облачные документы недоступны офлайн — понятная ошибка.
- Получение → «Файлы» → экспорт в выбранную папку; поддерживаемые форматы → медиатека; неподдерживаемые — сообщение об ошибке. Вставка через PasteButton, копирование полученного текста.
- Отключить Wi-Fi/усыпить Windows/уйти в фон iOS во время передачи; нажать отмену на каждом устройстве; переподключиться. При блокировке проверить Live Activity, обновление прогресса, завершение и истечение ограниченного фонового времени; запретить Live Activities в настройках и убедиться, что передача в приложении работает. Проверить, что незавершённые данные не появились в Received/Documents как готовые, и их нет после штатной отмены. После аварийного завершения повторно запустить Windows и проверить очистку Staging.
- Заполненный диск, запрет записи Received, конфликт имён и занятой порт. Ошибка не должна выглядеть как успешная доставка. После потери ответа на успешный приём допустима проверенная копия с числовым префиксом.
- Закрытие окна оставляет один процесс в трее; нажатие значка показывает окно, «Выход» завершает процесс. Второй экземпляр не удаляет staging первого.

## Измерения ресурсов (без заранее обещанных цифр)

Используйте **release**, запишите версию Windows, CPU, объём RAM, тип сети, размер файлов и хеш коммита. Не включайте процессы сборки в измерение.

1. Откройте Диспетчер задач → Подробности, добавьте CPU, время CPU, рабочий набор, пиковый рабочий набор, выделенную память (commit), IO read/write bytes, число потоков и дескрипторов. Выберите `localdrop.exe`.
2. После запуска оставьте программу в трее на 5 минут без телефона, затем на 5 минут с подключённым iPhone без передач. Запишите значения и прирост CPU time; не делайте вывод по одному мгновенному проценту. Средний процент одного ядра = прирост CPU seconds / интервал seconds × 100. Диспетчер задач может нормировать процент на все логические ядра — укажите метод.
3. Повторите с файлом 100 МБ и 5–10 ГБ в обе стороны, отдельно отметьте подготовку дисковой копии/хеша и сетевую передачу. Фиксируйте максимум рабочего набора/commit, среднюю CPU и скорость. Рост размера файла не должен давать соответствующий линейный рост RAM.
4. Повторите отмену и 50 последовательных передач, проверьте возврат памяти/дескрипторов и отсутствие роста очереди/оставшихся staging-файлов. Через Resource Monitor проверьте соединения только между LAN-устройствами; в простое нет сканирования адресов.
5. Для iPhone используйте Instruments Allocations/Time Profiler/Energy Log из Xcode со своей установленной подписанной сборкой. Измеряйте подготовку Photos/iCloud отдельно от LAN передачи. Проверьте блокировку экрана, фон и возвращение в приложение.

CPU кратковременно работает при TLS, SHA-256 и копировании диска; это ожидаемо. Rust Tokio и Win32 UI в ожидании блокируются на IO/сообщениях. В подключённом состоянии длинный запрос завершается примерно раз в 50 секунд; это не нулевой сетевой трафик. Конкретные цифры можно публиковать только после этих измерений.
